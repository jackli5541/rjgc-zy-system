# 并发与 TCP 连接检查

检查日期：2026-10-12。范围：启动与代理、数据库池及锁、实时通知、前端轮询、文件传输、提交与协作编辑、成绩查询、AI 流式接口、后台任务。

## 结论与截图解读

截图连接数纵轴 `750.000` 是 750 条，不是 75 万；蓝线平时约 320 条，峰值约 900 条，末段约 650–700 条。图例为“各种状态下的 TCP 连…”，且有多个系列；没有展开图例，不能确认各条线的具体状态，也不能把它们都当作 ESTABLISHED 或应用连接。

截图中网卡上行峰值约 4.8 Mbps，公网流出峰值约 3.4 Mbps，网络错误和丢包显示为 0。没有带宽套餐上限、CPU、内存、磁盘延迟和 API 响应时间，因此既不能证明服务器不足，也不能证明 50 人并发验收通过。若套餐仅 5 Mbps，公网峰值已有较高占用；若为 100 Mbps，则这段流量较小。

50 个在线页面通常有约 50 条 SSE 长连接，此外还有普通 HTTP、静态文件、数据库及 OSS 连接。代理部署还存在浏览器到代理、代理到 API 两段连接；Windows 本机回环连接可能显示两个端点。连接总数不能直接换算为用户数。约 900 条全状态连接值得查来源，但不是连接泄漏的证据。

本次是代码与配置审查，未连接生产服务器，未改运行配置或业务代码。Docker daemon 不可用，未运行隔离数据库测试或负载测试；按项目约定未运行 E2E。

## 已有保护与容量边界

- API 每进程数据库池为 30 常驻、30 溢出，最多 60 个 checkout；Windows 启动和 Linux 文档默认两个 API worker，API 池合计上限 120，后台任务另有独立池。容器 API 默认单 worker。该上限不代表实际物理 TCP 数，也不能直接解释图中总连接。
- 每 API worker 同步线程额度 80，高于数据库池 60；池满时部分线程会等待。未配置池/数据库锁等待的业务化超时响应；不要直接增加 worker，因为每个进程同时增加线程、数据库池和 realtime 轮询。
- 实时事件监听按 worker 共享轮询，空闲退避至 2 秒；并非每用户每 250ms 查一次事件表。SSE 认证使用短 Session，未把数据库连接占满整个长连接；每 15 秒心跳检查会话，50 页面约 3.3 次会话检查/秒。
- SSE 每 300 秒断开并重新建立，前端每次收到 sync_required 会重新取当前视图和通知；50 个页面可能形成周期性刷新波峰。前端安全刷新已有随机偏移，但 SSE 固定寿命没有抖动。
- Shell 切班及卸载会关闭 EventSource，队列有 32 条上限；这些地方未发现无限累积订阅的常规路径。
- 正式提交对 User/Team 及提交记录加锁，提交版本和幂等键有唯一约束；组员、签到、互评也有部分行锁/唯一约束。已有保护不等于所有组合并发情形已验证。
- 普通附件下载鉴权后重定向 OSS，能减轻应用服务器出口负担；部分文件预览和资料仍由 API 代理读取。GZip 的本地 Starlette 0.46.2 排除 SSE，未把 SSE 压缩认定为问题。
- 上传默认单文件上限 500 MiB；即使块读取减少内存使用，50 个同时上传的总带宽、临时磁盘与 OSS 时延仍须单独验收。名单导入为全量读取且没有独立小文件上限，是另一个资源边界缺口。

## 服务器只读取证

Windows 服务器使用管理员 PowerShell：

```powershell
.\scripts\inspect-tcp.ps1 -Samples 3 -IntervalSeconds 10 -OutputPath "$env:TEMP\coursework-tcp.json"
```

采集全机连接状态、进程和本地/远端端口聚合，不采集 IP、命令行、口令，不终止连接或修改配置。TIME_WAIT 的 PID 可能为 0，不能仅据此归责进程。全机结果还包括其他服务；需结合实际 API 端口、1433、远端 443 判断。保存的 JSON 不应提交仓库。

Linux 服务器可分别运行以下只读命令（若使用容器，也要检查容器网络命名空间；单看宿主机不能覆盖所有连接）：

```bash
ss -s
ss -Htan | awk '{count[$1]++} END {for (state in count) print state, count[state]}'
sudo ss -Htanp '( sport = :8000 or dport = :8000 )' | awk '{count[$1]++} END {for (state in count) print state, count[state]}'
```

解读：ESTABLISHED 随页面数大致稳定、停止访问后下降通常正常；TIME_WAIT 随请求上升后回落偏向短连接；CLOSE_WAIT 持续单调增加优先查未关闭响应；SYN_RECV 异常增多查入口及请求来源。不同端口、状态不能混为一个“连接数”。截图若是 Windows 云主机监控，则优先用上述 PowerShell 脚本验证。

同时补采 CPU（整体及 Python 进程）、可用内存、磁盘临时空间、API 请求速率/P95/5xx、SQL 活跃连接/锁等待/死锁、OSS 耗时及公网套餐限速。展开云监控 4 个连接系列的完整名称。

## 50 人并发验收方案

仅在隔离测试库和独立 OSS 前缀中进行。稳定阶段维持 50 个不同账号在线，执行总览、作业详情、通知、签到；另做集中提交、同组协作保存、附件预览中途取消、AI 混合负载、导出排队。每阶段记录基线、峰值和停止负载后的回落，不能以 50 个裸 health 请求代替真实用户。

建议初始验收目标（不是现有实测结果）：普通读接口 P95 小于 1 秒，非预期 5xx 小于 1%，SSE 首包/心跳持续正常，数据库 checkout 与 CLOSE_WAIT 不单调增长，同版本并发保存返回一成功一 409，任务异常退出后可恢复。上传和模型推理单独设耗时目标，不与普通读请求混算。

修复顺序：先量清状态与端口；再修协作版本、async 同步阻塞、长事务和流关闭；按部署路径处理代理复用；最后优化成绩取数、任务恢复并完成隔离并发验收。不要依据约 900 条全状态连接直接扩容或调整操作系统 TCP 参数。
