# AI 批改重新生成与等待时间修复

## 行为变化

主批改仍需返回有效 JSON、等级、定级理由、逐项证据和总评。主请求失败或超过原有 180 秒任务时限，任务仍报告失败；没有放宽评分结果校验。

理由超过 120 字符或总评超过 150 字符时，评语精简是可选步骤：最多调用一次，最多等待 5 秒，并预留约 1 秒保存结果。剩余时间不足时直接跳过。精简接口失败、返回非法 JSON、缺少字段、仍然过长或超时，均保留主批改的完整原结果；不会为了字数截断证据或重新评分。正常精简仅替换理由和总评，等级、证据及改进点不变。

因此正文可能超过建议字数，但不会仅因精简失败而丢失有效建议。真实模型速度、材料读取和数据库保存仍受部署环境影响，不保证固定完成秒数。

界面的历史对比已明确标为“上次 AI 建议”“本次 AI 建议”，历史理由也标明来自 AI，与学生互评、教师正式评分区分。

## 日志与任务追踪

Worker 领取和执行日志包括 `draft`（草稿 ID）、`run`（本轮运行 ID）、`job`（后台任务 ID）、`host`、`pid` 和 `code_version`。代码版本为相关 Python 源文件计算出的 SHA-256 指纹，统一换行符后取前 16 位，可识别未提交代码的差异，不依赖服务器安装 Git。

处理者信息保存于既有 `rubric_snapshot._run.worker`；失败阶段保存于 `_run.failed_stage`。没有新增数据库列，不需要数据库迁移。

阶段和耗时字段：

| 字段 | 含义 |
| --- | --- |
| `queue_seconds` | 排队时间 |
| `materials_ms` | 获取评分材料的时间 |
| `first_content_ms` | 模型首次返回正文的时间 |
| `generation_ms` | 主批改生成与解析时间 |
| `compact_ms` / `compact_outcome` | 精简耗时及 applied、invalid、skipped 或异常类型 |
| `save_ms` | 数据库结果保存时间，包含提交事务 |
| `total_ms` / `duration_ms` | Worker 执行总耗时，失败时为 duration_ms |
| `stage` | LOAD、MATERIALS、GENERATING 或 SAVING 失败阶段 |

异常保留后台堆栈。排查时用同一个 `job` 和 `run` 查找领取、执行和失败记录，不仅凭页面通用错误推断模型、OSS 或数据库故障。如果数据库记录已变更而当前 Worker 完全没有对应领取记录，应收集其他连接同一数据库的 Worker 日志，核对代码和配置版本。

客户截图对应的失败异常尚未从实际处理者日志确认。本次修复的是代码中已确认的可选精简错误传播问题，并补齐定位依据；不把多 Worker 或精简错误作为截图的已证实根因。

## 客户自行部署

1. 从 Git 获取包含此次修复的代码，统一更新 API 和所有 Worker，避免同一数据库混跑旧版本。
2. 按 `AI独立配置.md` 配置公共 `AI_PROVIDER`、`AI_BASE_URL`、`AI_API_KEY`、`AI_CHAT_MODEL`、`AI_REQUEST_TIMEOUT_SECONDS`；分别启用教师与批改，旧模块专用接口变量不再生效。
3. 客户按部署环境自行配置数据库与 OSS。本地 `.env` 不提交 Git，不能直接覆盖客户 `.env`。
4. 在 `frontend` 执行 `npm run build`，部署整个 `dist`（含 index.html 与 assets）；如使用 CDN，同步更新对应资源。
5. 重启全部 API 和 Worker，刷新浏览器，确认“上次 AI 建议”文案及学生批注下方的 AI 面板。再次失败时收集对应任务 ID、运行 ID 及后台堆栈。

本次不要求新增数据库、数据库迁移或初始化教师账号，也未操作客户服务器。

以下为初次修复时的历史记录；后续交付验证及限制以 `AI修复交付说明.md` 为准。本地验收环境随后已改为独立测试库，不使用客户业务库。
