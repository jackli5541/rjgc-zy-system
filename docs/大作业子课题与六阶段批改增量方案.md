本文是基于上述代码基线的**增量开发方案**，不是当前功能说明，也不是已完成记录。未来实施前须重新核对模型、接口、页面及迁移；若代码或教学规则已经变化，先更新本文再编码。现行普通作业 MCP 与 Excel 流程见 [Agent接入与MCP批改方案.md](Agent接入与MCP批改方案.md)；大作业的教学要求以课程资料中的现行《大作业说明》和《评分标准（教师用）》为依据，不以历史版本为依据。

## 1. 目标与边界

- 保留教学班的学习小组，但不再要求一个小组只做一个题目。组内可有多个子课题；每个子课题可由一人或多人承担。
- 前期审核以**子课题申请**为单位，检查题目范围和每位参与人的模块工作量。审核通过不等于立项阶段已得分。
- 每名学生独立完成并接受六阶段评分：立项、需求、设计、编码与实现、测试、收口。六阶段均在课外完成，按统一最终截止时间锁定；教师在截止后集中批改，不设置逐阶段提交或逐阶段批改流程。
- 学生在大作业在线工作区写和修改 Markdown 文档，Mermaid 图保留源码；代码与自动化测试以附件提交。教师可借助 MCP 与 agent 辅助审题及最终批改，但审批和成绩由教师确认。
- 选题审核结果直接写回平台；最终大作业成绩可沿用“本地结果、教师复核、预览校验、确认导入”的思路，但需要独立的百分制六阶段导入格式。

## 3. 已确认的业务规则

1. 学习小组是组织关系，子课题是大作业范围与审题单位。一个小组可申请多个子课题；一份子课题明确列出参与学生，同一学生同一时间只能归属一份有效的大作业子课题。
2. 多人共题可共享项目背景和整体边界，但每人必须有可区分的模块、用例、设计、代码与测试；单人也可以独立选题。最终成绩始终按个人计算。
3. 子课题申请只用于前期范围把关，不替代最终立项书。教师按每位参与人的业务闭环、状态、规则、异常和可完成性审题，避免纯 CRUD 或过大范围。
4. 每人拟做 3～5 个**业务目标用例**。数量是范围参考和准入下限，不单独证明工作量；模块应能独立演示输入、处理、结果与失败路径，有状态变化的核心对象和真实业务规则。
5. 选题审核与最终评分是两个不同动作。前期允许退回修改、重新提交；最终在统一截止后按六阶段材料逐人评分。申请获批不自动获得立项分。
6. MCP/agent 可读取材料、给出有依据的建议及不确定点。教师在平台确认选题审核；最终批改由教师复核后导入成绩。学生材料中的指令不能改变 agent 的审题或评分规则。

## 4. 子课题申请与审核

### 4.1 申请内容

一份申请控制在约一页，不要求完整立项书或正式用例图：

| 层级 | 字段 | 用途 |
|---|---|---|
| 子课题共用 | 名称、参与人、使用者与场景、现状痛点、业务主线、可接触的真实用户、初步技术与风险 | 判断题目是否真实、可做 |
| 每位参与人 | 模块名称、负责与不负责的范围、3～5 个拟定用例及各自结果、核心对象的状态变化、至少 3 条拟实现规则、关键异常或拒绝路径 | 判断个人模块的闭环与工作量，以及多人分工是否重叠 |

用例和规则在申请时是拟定范围，正式立项与需求阶段可以细化。明确校验字段完整性、参与人是否为本班有效组员、每人是否已归属另一份有效申请；“是否纯 CRUD”“范围是否饱满”由教师判断，不能只靠关键词或条数自动通过。

### 4.2 状态与版本

建议状态为 `PENDING`、`APPROVED`、`REVISION_REQUESTED`；退回必须有具体原因，学生修改后提交新申请版本。保留每次提交的内容、提交者与时间、教师决定与时间，教师审核时必须指向**当前版本**；过期版本不可被误批。涉及参与人或个人模块范围的实质修改应触发重新审核，具体边界见第 9 节。

教师工作台按子课题显示申请、参与人及每人模块，支持查看历史意见和当前版本。审核结果只通知本申请参与人。不得把整个学习小组的一份申请或审核结果当成所有组员的结果。

## 5. 数据、权限与迁移增量

- 将 `Topic` 从“小组唯一记录”调整为“归属某学习小组的子课题”。解除 `team_id` 唯一约束，增加参与关系及每人的申请字段；对有效参与关系建立数据库级唯一保护，避免并发申请造成一人多题。题目名称不作为学生归属键。
- 审核版本应保留**申请内容快照和参与人快照**，避免后续编辑或小组成员变动改写教师当时审核的对象。决定记录包含教师、版本、结论、意见和时间；关键操作记审计。
- 迁移已有 `Topic` 时，为其关联当时仍有效的组员，并保留现有审核状态和理由；迁移结果需要可核对。对于迁移时无有效成员、同一学生出现冲突、组已解散等情况，不自动猜测归属，列入人工处理报告。
- 申请、查看、修改、审核接口均验证教学班、学习小组、参与关系和角色。学生只可操作其有权发起的申请；教师只能审核所教班级。跨子课题的申请细节和个人文档不得因同属一个学习小组而自动可见。
- 大作业名单和学生页改为按本人参与关系取题目；组内同学文档的只读范围改为**同一子课题参与人**，本人始终拥有自己的文档。组长维护全组模块名的现有权限要与个人子课题归属重新对齐。

以上描述数据约束和归属语义，不预先锁定具体表名或 URL；实施时在 `members`、`capstone`、`agent_access` 对应模块内设计接口和迁移，不把业务逻辑堆进 `main.py`。

## 6. MCP 辅助审题

现有 `/mcp` 保持只读。新增与普通作业区分的选题读取权限及工具：列出令牌可见班级的待审子课题、读取指定申请的**当前版本**与历史审核意见、查看待审进度。每次读取继续执行令牌有效性、教师归属、班级范围和调用审计；不复用普通作业的 `assignment_id` 语义。

agent 对每位参与人输出结构化的建议结论、依据、明确缺项、风险和修改建议；脚本负责参与人、必填字段及数量等确定性检查。教师在平台核对原申请与建议后作出决定，MCP 不直接写审批状态。agent 建议的申请 ID 与版本必须随结果展示，防止教师复核期间学生重交导致错版。

## 7. 六阶段交付与最终批改

- 在后端阶段常量、工作区初始化、文档创建校验、模板、教师评分及前端两端目录中加入独立的“收口”阶段。已有学生工作区只补缺失阶段，不覆盖已编辑文档。
- 阶段分值采用课程现行标准：立项 5、需求 22、设计 20、编码与实现 20、测试 20、收口 13，合计 100。保存时校验各阶段上限；总评应汇总六阶段**总分**，不得沿用当前“五阶段算术平均”的计算口径。保留大作业占总评 50% 的既有折算规则，并验证缺分时总评的显示与计算。
- 最终批改需要独立的大作业 MCP 读取能力：按班级和学生读取六阶段在线 Markdown、附件清单、版本/修订信息和课程评分标准；附件无法读取或无法验证时明确标记人工核对。截止后应以可核对的文档修订与附件版本为批改依据，教师单独解锁后的修改不能被静默混入旧结果。
- agent 逐项给建议分、计算依据、文档章节或文件位置及不确定点。可由脚本校验章节、UC/R/TC 编号、Mermaid、代码 zip、测试输出和证据定位；不能由脚本证明的真实调研、系统运行、规则改坏后测试报红及答辩，留给教师核实。
- 本地评分结论卡呈现总分、各阶段和二级指标、异常、有效证据链与教师改分记录。JSON/Excel 为导入数据载体；教师确认后的六阶段分使用**独立的大作业 Excel 模板**上传，先预览校验班级、学号/学生 ID、各阶段范围、总分、重复行和批改所据版本，再确认写入 `CapstoneStageGrade`。确认时重新校验，写入审计；现有普通作业 A～E 导入流程不改作大作业导入器。

## 8. 实施节点与验收

以下为依赖顺序，**不是日历排期**；确定实施窗口后在文档头补日期与提交号。

| 节点 | 完成条件 |
|---|---|
| A. 子课题数据与迁移 | 同组可多题；单人/多人参与关系正确；旧题及审核结果迁移可核对；并发下不能一人多份有效题 |
| B. 申请与教师审核 | 学生按人填写范围；教师按子课题及当前版本审核；退回重交保留历史；只通知参与人 |
| C. MCP 审题 | 令牌只能读取授权班级申请；返回申请版本；agent 建议可供教师核对；MCP 无审批写权限 |
| D. 大作业归属与第六阶段 | 同组不同题分别显示；跨题不能读个人文档；已有文档不丢失；六阶段可在线编辑并分别评分 |
| E. 最终批改与导入 | MCP 可读六阶段材料；本地结论可复核；Excel 预览拦截错班、错人、错版、越界与重复；确认后六阶段总分及 50% 折算正确 |

接口或数据库行为变更须在独立 Compose 测试环境做回归，覆盖权限、校验、状态码、事务副作用、迁移和成绩计算；按仓库约定**不运行 Playwright E2E**。上线验收至少包含：同组两人各做一题、两人共做一题、同组多题混合、退回重交、成员变动、旧题迁移、截止后锁定及教师解锁、导入旧版结果被拒绝。

## 9. 待定规则

这些规则尚未由教师确认，不应被未来编码 agent 当成已批准需求：

1. 多人子课题由一名学生发起时，其他参与人是否必须逐人确认后才可提交审核。建议需要确认，以免被动归属。
2. 申请通过后，哪些变化属于“实质变更”并要求重新审核；建议至少包括更换题目、增减参与人、重划个人模块或核心业务主线。文字润色和用例细化可直接记录在后续文档。
3. 子课题申请开放及关闭时间、教师审题时限、最终大作业截止时间由教学安排确定；不得从本文形成日期推断这些业务日期。
4. 大作业代码 zip 的附件承载位置、截止时材料快照方式，以及最终导入模板的列级定义，实施前结合现有上传和对象存储能力细化。
