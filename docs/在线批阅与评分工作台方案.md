# 在线批阅与评分工作台方案

## 1. 文档信息

- 适用项目：软件工程作业系统
- 方案状态：已确认，待排期实施
- 目标版本：第一阶段在线评分工作台
- 后续可选：第二阶段文档定位批注
- 文档原则：优先完成高频评分流程，不提前建设尚未确定使用的批注和文档转码能力

## 2. 背景与问题

当前系统已经支持 PDF、Markdown 和图片在线预览，也支持学生互评、教师查看提交、成绩生成与发布，但评分与预览仍是分离的：

1. 学生需要先查看文件，再回到页面下方填写分数和评语。
2. 教师查看学生提交时，需要在提交列表、详情弹窗和成绩页面之间往返。
3. 当前预览抽屉只负责文件展示，不显示当前被评价学生，也不能连续切换学生。
4. 评分过程中没有统一的自动保存机制。
5. 当前成绩模型以学生互评分和小组系数为主，尚未支持教师逐人评价及“教师分优先”的成绩规则。
6. 当前 PDF 使用浏览器原生预览，适合阅读，但不能承载精确到页面位置的批注。

本方案将教师评价和学生互评统一为相同的在线评分体验，同时控制改造范围。第一阶段不实现文档定位批注，不引入 PDF.js，不建设 Office 转 PDF 链路。

## 3. 已确认的业务规则

### 3.1 教师评价与学生互评

教师评价和学生互评使用相同的评价规则：

- 都针对某个学生的一次正式提交版本进行评价。
- 都包含 0 至 100 分的分数和总体评语。
- 都支持未完成草稿和已完成评价两种状态。
- 都采用自动保存，不提供手动“保存”或“提交”按钮。
- 分数和评语满足完整性要求后，评价自动成为已完成状态。
- 只有已完成评价才能参与最终成绩计算。

教师和学生的区别只体现在评价对象来源及权限：

- 教师评价队列来自该作业的正式提交名单。
- 学生互评队列来自系统生成的互评分配结果。
- 教师可以查看当前教学班内该作业的全部提交。
- 学生只能查看分配给自己的评价对象及冻结提交版本。

### 3.2 最终成绩

最终成绩采用教师评价优先、学生互评兜底的规则：

```text
如果存在已完成的教师评价：
    最终分 = 教师分
    成绩来源 = TEACHER
否则，如果存在已完成且有效的学生互评：
    最终分 = 学生互评分
    成绩来源 = PEER
否则：
    最终分 = 空
    成绩来源 = 空
```

补充规则：

- 教师评价仍为草稿时，不覆盖已经完成的学生互评分。
- 教师完成评分后，成绩草稿立即切换为教师分。
- 教师清空或撤销自己的未发布评价后，成绩草稿回退到有效学生互评分。
- 两类评价都不存在或都未完成时，学生成绩保持待处理。
- 教师分、学生互评分和最终采用来源需要分别保存，不能互相覆盖。
- 当前“小组系数 × 互评分”的计算方式退出新成绩主流程，避免与教师分优先规则冲突。
- 历史成绩仍按原记录展示，不反向重算。

### 3.3 文档类型

第一阶段只覆盖项目实际使用的文件类型：

- PDF
- Markdown
- PNG、JPG、JPEG、GIF、WebP 等图片

第一阶段不建设 DOCX、PPTX、XLSX 在线转码能力。这些格式继续沿用现有下载处理，不纳入本次批阅工作台的核心验收范围。

## 4. 目标与非目标

### 4.1 第一阶段目标

1. 教师和学生直接在文档预览工作台内评分和填写总体评语。
2. 顶部持续显示当前被评价学生、学号和队列进度。
3. 评分面板随批阅过程持续可见，但不覆盖文档内容。
4. 支持方向键连续切换学生和文件。
5. 所有评价变更自动保存。
6. 教师评价和学生互评共用一套前端交互、校验规则和自动保存机制。
7. 最终成绩按“教师已完成评分优先，否则使用已完成学生互评”计算。
8. 保留评价与正式提交版本的关联，避免学生重新提交后评价错位。
9. 完成权限、并发、失败恢复、成绩发布和回归测试闭环。

### 4.2 第一阶段非目标

第一阶段明确不做：

- PDF 页面内圈选、画框、点位或文字选区批注。
- PDF.js 集成。
- 图片坐标批注层。
- Markdown 文字锚点。
- 批注数据库表和批注 API。
- Office 文档转 PDF。
- 统一把所有文件转换成同一种格式。
- 实时协同编辑或 WebSocket 推送。
- 多教师同时批改同一学生的复杂合并规则。

## 5. 总体方案

系统新增统一的“在线批阅工作台”。工作台负责队列导航、文件预览、评价输入和自动保存，教师评价与学生互评复用同一套工作台。

```text
批阅入口
  -> 加载评价队列
  -> 定位当前学生和冻结提交版本
  -> 加载当前文件预览
  -> 加载该评价人的评价草稿
  -> 自动保存分数和总体评语
  -> 自动计算评价完成状态
  -> 更新成绩草稿及成绩来源
  -> 切换下一位学生或下一个文件
```

第一阶段统一的是批阅外壳和评价流程，而不是文档内容格式。PDF、Markdown 和图片继续使用现有预览能力。

## 6. 工作台交互设计

### 6.1 页面布局

桌面端采用三段式布局：

```text
┌──────────────────────────────────────────────────────────────┐
│ 作业名称 | 当前学生：李同学 20260002 | 8/36 | 自动保存状态 │
├───────────────────────────────────────────┬──────────────────┤
│                                           │ 分数             │
│                                           │ 总体评语         │
│                文档预览                   │ 评价完成状态     │
│                独立滚动                   │                  │
│                                           │                  │
├───────────────────────────────────────────┴──────────────────┤
│ 文件信息、当前文件序号、下载原文件                         │
└──────────────────────────────────────────────────────────────┘
```

布局要求：

- 顶部信息栏固定在工作台顶部。
- 文档区域独立滚动，不推动评分面板离开视口。
- 评分面板占用独立布局宽度，建议桌面端为 300 至 340 像素。
- 评分面板不得以悬浮层覆盖文档。
- 评分面板允许折叠成窄工具条，以便查看横向内容较多的 PDF 或图片。
- 移动端采用文档全宽加底部评分抽屉，不强制并排显示。
- 文件预览失败时仍保留评分面板，用户可以下载原文件后继续评分。

### 6.2 顶部信息栏

顶部信息栏持续显示：

- 作业名称。
- 当前学生姓名。
- 当前学生学号。
- 当前队列位置，例如 `8 / 36`。
- 当前评价状态：未开始、草稿、已完成。
- 自动保存状态：正在保存、已保存、保存失败正在重试。
- 返回列表或关闭工作台入口。

教师批阅小组作业时，当前对象显示小组名称和成员快照；个人作业显示学生姓名和学号。

### 6.3 键盘操作

- `↑`：切换到上一位学生。
- `↓`：切换到下一位学生。
- `←`：切换到当前学生的上一个文件。
- `→`：切换到当前学生的下一个文件。

避免误操作的规则：

- 当焦点位于输入框、文本域、数字输入框或其他可编辑元素时，方向键只用于编辑内容，不触发工作台切换。
- 当前存在未完成保存请求时，切换操作先等待保存完成。
- 保存失败时不执行切换，并展示明确的失败状态。
- 到达队列或文件边界后不循环跳转，按钮和快捷键进入禁用状态。
- 文档上下滚动使用鼠标滚轮、触控板、滚动条以及 `PageUp`、`PageDown`。

### 6.4 队列顺序

教师队列默认按学号升序排列，并继承提交看板当前筛选条件：

- 全部
- 已提交
- 未提交
- 迟交
- 小组
- 关键词

只有存在正式提交文件的对象可以进入正常预览评分。未提交对象可以保留在队列中展示状态，但不允许创建已完成评价。

学生队列来自服务端互评分配。当前一对一互评下通常只有一名评价对象，此时上下切换自动禁用。未来如果业务调整为一人评价多人，工作台无须重做，只需要服务端返回多条分配记录。

### 6.5 文件切换

- 文件顺序采用冻结提交版本中的文件顺序。
- 顶部或底部显示当前文件名及 `1 / 3` 等序号。
- 左右键和可见图标按钮执行相同操作。
- 文件切换不清空分数和总体评语。
- 评价绑定整个提交版本，不绑定单个文件。
- 下载原文件始终可用。

## 7. 预览技术方案

### 7.1 第一阶段保留现有能力

- PDF：继续使用浏览器原生 PDF 阅读器。
- Markdown：继续由服务端转换并清洗为安全 HTML，再通过预览容器展示。
- 图片：继续使用图片元素按容器缩放显示。

前端增加统一的 `ReviewViewer` 外壳：

```text
ReviewWorkspace
├── ReviewHeader
├── ReviewViewer
│   ├── PdfPreview
│   ├── MarkdownPreview
│   └── ImagePreview
└── EvaluationPanel
```

`ReviewViewer` 只统一以下能力：

- 加载状态。
- 预览错误状态。
- 文件序号和切换。
- 下载原文件。
- 当前 `file_id` 和 `submission_version_id` 上下文。

第一阶段不统一各格式的内部渲染方式。

### 7.2 安全要求

- PDF 和图片继续通过已有文件访问授权校验后返回。
- Markdown 必须继续执行 HTML 清洗，禁止脚本、事件属性和危险链接。
- 预览接口不能绕过教师所属教学班、学生评价分配和文件归属校验。
- 前端隐藏入口不能代替服务端权限校验。

## 8. 评价状态与自动保存

### 8.1 状态定义

教师评价和学生互评统一采用以下状态语义：

| 状态 | 含义 | 是否参与成绩计算 |
|---|---|---|
| `DRAFT` | 已有部分输入，但未满足完整评价要求 | 否 |
| `COMPLETED` | 分数和必填评语均满足规则 | 是 |
| `INVALID` | 学生互评被教师作废 | 否 |

教师评价第一阶段不提供单独作废状态。教师可以在成绩发布前继续修改或清空草稿；已发布后修改需要进入现有成绩修订流程。

### 8.2 自动完成条件

评价满足以下条件时自动成为 `COMPLETED`：

- 分数不为空。
- 分数在 0 至 100 范围内。
- 分数符合接口允许的精度。
- 总体评语去除首尾空白后达到配置的最小长度。

任何条件不满足时保存为 `DRAFT`。系统不能因为字段暂时为空而丢弃用户已输入的其他内容。

### 8.3 保存触发

- 分数变化后约 500 毫秒防抖保存。
- 总体评语变化后约 800 毫秒防抖保存。
- 失焦时立即刷新防抖队列并保存。
- 切换学生、离开工作台和关闭页面前刷新待保存请求。
- 相同内容不得重复写入数据库和审计日志。

### 8.4 并发与请求顺序

每条评价包含 `version` 字段：

1. 客户端提交当前版本号。
2. 服务端使用行锁或条件更新保存内容。
3. 保存成功后版本号加一并返回完整评价。
4. 版本冲突返回 `409` 和最新服务端内容。
5. 前端不得让较早请求的响应覆盖较新输入。

前端为每条评价维护递增的请求序号。只有最新请求可以更新本地“已保存”状态。

### 8.5 保存失败恢复

- 网络错误后采用有限次数指数退避重试。
- 重试期间持续显示“保存失败，正在重试”。
- 重试失败后保留本地输入，不清空表单。
- 保存未成功时禁止切换学生，避免用户误认为内容已经保存。
- 可以使用 `sessionStorage` 暂存当前评价的未保存内容，但数据库仍是最终事实来源。
- 恢复网络后优先提交本地未保存内容，并通过版本号检测冲突。

## 9. 数据模型调整

### 9.1 学生互评

保留现有 `peer_reviews` 表和业务关系，做最小调整：

- `total_score` 调整为可空。
- `comment` 允许空字符串。
- `scores` 允许空对象。
- `status` 支持 `DRAFT`、`COMPLETED`、`INVALID`。
- 保留 `allocation_id`、`campaign_id`、`reviewer_id`、`reviewee_id` 和 `submission_version_id`。
- 保留学生互评作废和审计能力。

迁移时将现有有效评价状态从 `VALID` 映射为 `COMPLETED`，或者在兼容期同时识别两种状态，待数据迁移完成后再移除 `VALID`。

### 9.2 教师评价

新增 `teacher_evaluations`：

| 字段 | 说明 |
|---|---|
| `id` | 教师评价 ID |
| `assignment_id` | 作业 ID |
| `subject_user_id` | 被评价学生 ID |
| `submission_version_id` | 被评价正式提交版本 ID |
| `teacher_id` | 评价教师 ID |
| `score` | 教师分，可空 |
| `comment` | 教师总体评语 |
| `status` | `DRAFT` 或 `COMPLETED` |
| `version` | 乐观锁版本号 |
| `created_at` | 创建时间 |
| `updated_at` | 最后修改时间 |

建议唯一约束：

```text
(assignment_id, subject_user_id, teacher_id)
```

如果未来一个教学班支持多名教师，可以保留多名教师分别评价的记录，但第一阶段最终成绩只认作业所属教师或当前主教师的评价。

### 9.3 成绩记录

现有 `grades` 至少需要支持：

| 字段 | 说明 |
|---|---|
| `peer_score` | 已完成且有效的学生互评分 |
| `teacher_score` | 已完成的教师分 |
| `draft_score` | 当前待发布最终分 |
| `score` | 已发布最终分 |
| `draft_score_source` | 当前草稿来源：`TEACHER` 或 `PEER` |
| `score_source` | 已发布成绩来源 |
| `teacher_evaluation_id` | 当前采用的教师评价，可空 |
| `peer_review_id` | 当前采用的学生互评，可空 |
| `status` | 待处理、草稿、已发布或已变更 |
| `version` | 成绩版本 |

`campaign_id` 应允许为空，使没有学生互评活动但教师已评分的作业也能生成成绩记录。

### 9.4 成绩修订记录

成绩修订记录需要补充：

- 原成绩来源。
- 新成绩来源。
- 原教师分。
- 原学生互评分。
- 原最终分。
- 修改原因。
- 修改教师和修改时间。

已发布成绩发生以下变化时必须填写修订原因：

- 教师首次评分导致成绩从学生互评分切换为教师分。
- 教师修改已发布教师分。
- 教师撤销评分导致成绩回退到学生互评分。
- 学生互评被作废且没有教师分可兜底。

## 10. 服务端接口方案

接口继续位于 `/api/v1` 下。

### 10.1 教师批阅队列

```http
GET /assignments/{assignment_id}/grading-queue
```

查询参数支持提交状态、小组和关键词筛选。响应包含：

- 作业信息。
- 队列顺序。
- 学生或小组信息。
- 正式提交版本。
- 文件列表。
- 当前教师评价。
- 当前学生互评摘要。
- 当前成绩草稿及来源。

服务端应一次返回队列摘要，当前条目的详细预览数据可以按需加载，避免一次返回全班所有文件详情。

### 10.2 学生批阅队列

```http
GET /review-campaigns/{campaign_id}/grading-queue
```

响应仅包含当前学生被授权的互评分配。当前一对一规则下通常只有一条。

### 10.3 教师评价自动保存

```http
PUT /assignments/{assignment_id}/teacher-evaluations/{subject_user_id}
```

请求示例：

```json
{
  "submission_version_id": "uuid",
  "score": 92,
  "comment": "结构完整，需求分析较清晰。",
  "version": 3
}
```

服务端自动判断 `DRAFT` 或 `COMPLETED`，客户端不能自行指定完成状态。

### 10.4 学生互评自动保存

建议将现有创建式接口调整为幂等保存：

```http
PUT /review-campaigns/{campaign_id}/evaluations/current
```

请求包含分数、总体评语和版本号。服务端根据当前登录学生查找其唯一分配，不接受客户端自由传入被评价学生 ID。

### 10.5 响应结构

教师评价和学生互评接口返回统一评价结构：

```json
{
  "id": "uuid",
  "evaluation_type": "TEACHER",
  "score": 92,
  "comment": "结构完整，需求分析较清晰。",
  "status": "COMPLETED",
  "version": 4,
  "saved_at": "2026-09-16T15:30:00+08:00",
  "grade": {
    "peer_score": 88,
    "teacher_score": 92,
    "draft_score": 92,
    "draft_score_source": "TEACHER"
  }
}
```

### 10.6 学生查看结果

现有学生成绩接口增加：

- `peer_score`
- `teacher_score`
- `score`
- `score_source`
- 教师总体评语
- 学生互评总体评语

只有已发布成绩及已允许公开的评价内容可以返回给学生。教师评分草稿不能提前暴露。

## 11. 成绩生成与发布流程

### 11.1 草稿重算

以下事件触发单人成绩草稿重算：

- 学生互评首次成为 `COMPLETED`。
- 学生互评从 `COMPLETED` 退回 `DRAFT`。
- 学生互评被作废。
- 教师评价首次成为 `COMPLETED`。
- 教师评价从 `COMPLETED` 退回 `DRAFT`。
- 教师修改已完成评分。

重算只影响对应学生，不需要重算整份作业。

### 11.2 发布隔离

- 自动保存只更新评价和成绩草稿。
- 学生在教师执行成绩发布前仍看到旧的已发布成绩。
- 草稿最终分和已发布最终分必须分开保存。
- 已发布成绩变化时沿用修改原因和修订记录要求。
- 待处理学生不阻止其他可发布学生发布。

### 11.3 导出

成绩导出建议调整为：

- 作业
- 学号
- 姓名
- 小组
- 学生互评分
- 教师分
- 草稿最终分
- 草稿来源
- 已发布最终分
- 已发布来源
- 状态

原小组系数列只为历史作业保留，不再作为新评分规则的必填字段。

## 12. 权限与数据可见性

### 12.1 教师

- 只能评价自己可管理教学班内的作业提交。
- 评价必须绑定该作业当前正式提交版本。
- 不能通过修改请求参数评价其他教学班学生。
- 可以查看该作业全部学生互评及教师评价。
- 可以在成绩发布前修改教师评价。
- 修改已发布成绩必须填写原因并保留历史。

### 12.2 学生评价人

- 只能读取系统分配给自己的评价对象。
- 只能评价冻结的提交版本。
- 不能自评、换人或修改 `reviewee_id`。
- 只能在活动截止前自动保存和修改。
- 截止后评价只读。

### 12.3 被评价学生

- 成绩发布前不能看到教师评价草稿。
- 成绩发布后只能看到自己的分数、来源和评价内容。
- 不能查看其他学生的教师评价或互评。

## 13. 前端状态管理

工作台至少维护：

```text
queue
queueIndex
activeSubject
files
fileIndex
evaluationDraft
serverEvaluation
saveState
saveSequence
pendingSave
previewState
```

建议将评分工作台拆为独立组件，而不是继续把逻辑全部堆叠在 `ShellView.vue` 中：

- `ReviewWorkspace.vue`
- `ReviewHeader.vue`
- `ReviewViewer.vue`
- `EvaluationPanel.vue`

第一阶段不需要抽象复杂的插件系统，只要保证教师入口和学生入口传入相同的工作台数据结构即可。

## 14. 数据迁移与兼容

建议新增一条 Alembic 迁移完成：

1. 新建 `teacher_evaluations`。
2. 调整 `peer_reviews` 草稿所需字段和状态。
3. 调整 `grades.campaign_id` 为可空。
4. 为 `grades` 增加教师分和成绩来源字段。
5. 为 `grade_revisions` 增加来源相关字段。
6. 为关键查询添加组合索引。

历史数据处理：

- 现有有效学生互评继续作为 `peer_score`。
- 已发布历史成绩保留原值，不自动套用新规则。
- 现有小组系数和历史修订记录保留。
- 新规则只对迁移后新生成或重新编辑的成绩草稿生效。
- 如需让旧作业切换新规则，应由教师显式触发，不在迁移中批量重算。

## 15. 审计要求

以下操作写入审计日志：

- 教师评价首次成为已完成。
- 教师已完成评价的分数发生变化。
- 教师评价被清空或退回草稿。
- 学生互评首次成为已完成。
- 学生已完成评价发生变化。
- 学生互评被作废。
- 成绩来源从学生互评切换为教师评价。
- 成绩来源从教师评价回退为学生互评。
- 成绩发布和重新发布。

自动保存每次键入不应产生一条审计日志。只有状态或影响成绩的关键字段发生实质变化时记录审计事件。

## 16. 测试方案

### 16.1 后端测试

必须覆盖：

1. 教师只能评价自己管理班级的学生。
2. 学生只能评价服务端分配的对象。
3. 分数为空时可以保存草稿。
4. 评语为空或不足时可以保存草稿，但不能完成。
5. 分数越界仍返回参数校验错误。
6. 内容满足规则后自动成为 `COMPLETED`。
7. 教师草稿不覆盖学生互评分。
8. 教师完成评分后最终成绩草稿切换为教师分。
9. 教师评价退回草稿后回退到学生互评分。
10. 两类评分均不存在时成绩保持待处理。
11. 已发布成绩不会被自动保存直接覆盖。
12. 修改已发布成绩时要求修改原因并生成修订记录。
13. 版本冲突返回 `409`，不会静默覆盖。
14. 互评截止后不能继续保存。
15. 历史成绩不会在迁移后被自动重算。

### 16.2 端到端测试

桌面端至少覆盖：

1. 教师从提交看板进入批阅工作台。
2. 顶部显示当前学生、学号和队列进度。
3. PDF、Markdown 和图片均能在工作台内预览。
4. 修改分数后出现“正在保存”，随后变为“已保存”。
5. 修改评语后自动保存，不存在手动保存按钮。
6. 上下键切换学生。
7. 左右键切换文件。
8. 输入框内使用方向键不会切换学生或文件。
9. 保存失败时不允许切换学生，恢复后可以继续。
10. 学生端复用同一评分面板并自动完成评价。
11. 教师评分后成绩草稿来源显示为教师。
12. 没有教师评分时成绩草稿来源显示为学生互评。

移动端至少覆盖：

- 文档预览和底部评分抽屉不相互遮挡。
- 长评语不会撑破页面宽度。
- 文件切换和保存状态可见。
- 不依赖键盘也可以完成全部操作。

## 17. 验收标准

第一阶段完成需同时满足：

1. 教师和学生都可以在预览工作台内评分和填写总体评语。
2. 页面中不存在必须手动点击的保存或提交按钮。
3. 任意评价变更均可自动保存，并显示准确保存状态。
4. 教师端可以使用上下键连续切换学生。
5. 有多个文件时可以使用左右键切换文件。
6. 顶部持续显示当前学生身份和队列进度。
7. 评分面板不覆盖 PDF、Markdown 或图片内容。
8. 教师已完成评分时最终成绩草稿采用教师分。
9. 教师未完成评分时最终成绩草稿采用已完成学生互评分。
10. 自动保存不能直接改变学生已看到的已发布成绩。
11. 权限校验、版本冲突、断网恢复和截止时间均有回归测试。
12. 第一阶段没有引入 PDF.js、Office 转码或批注表。

## 18. 实施拆分与工作量

### 18.1 第一阶段

建议按以下顺序实施：

1. 数据库迁移和统一评价状态规则。
2. 教师评价接口和学生互评幂等自动保存接口。
3. 教师优先的成绩草稿计算与发布兼容。
4. 统一批阅队列接口。
5. 前端批阅工作台和预览外壳。
6. 自动保存、并发控制和失败恢复。
7. 键盘切换与响应式布局。
8. 后端、端到端和移动端回归测试。
9. 接口、架构和验收文档同步更新。

预计工作量为 6 至 9 个开发日，具体取决于历史成绩兼容范围和端到端测试环境稳定性。

### 18.2 第二阶段：可选定位批注

只有在确认业务确实需要后再启动：

1. PDF 预览从浏览器原生阅读器切换为 PDF.js。
2. 图片增加坐标覆盖层。
3. Markdown 增加文字引用锚点。
4. 新增批注数据模型、权限和接口。
5. 批注绑定 `submission_version_id`、`file_id`、页码及归一化坐标。
6. 成绩发布后向对应学生展示批注。

预计额外工作量为 5 至 8 个开发日。该阶段应独立评审、独立排期，不提前在第一阶段创建无用基础设施。

## 19. 风险与控制

### 19.1 方向键与文档操作冲突

控制方式：输入控件内不拦截方向键；文档滚动使用滚轮和 `PageUp/PageDown`；界面同时保留可见切换按钮。

### 19.2 高频自动保存导致请求过多

控制方式：防抖、内容去重、单评价串行写入和最新请求序号控制。

### 19.3 快速切换造成数据丢失

控制方式：切换前刷新保存队列；保存失败时阻止切换；保留本地未保存内容。

### 19.4 教师分覆盖规则引发历史成绩变化

控制方式：新规则只更新成绩草稿；历史已发布成绩不自动重算；重新发布必须留痕。

### 19.5 为未来批注过度设计

控制方式：第一阶段只保证评价绑定提交版本、预览知道当前文件，不创建批注相关模型和渲染层。

## 20. 最终决策摘要

本方案最终确定：

- 教师评价与学生互评采用相同的分数、总体评语、草稿和自动完成规则。
- 所有变更自动保存，不提供手动保存或提交按钮。
- 上下键切换学生，左右键切换文件。
- 顶部持续显示当前学生身份、队列进度和保存状态。
- 评分面板与文档并排，不遮挡文档。
- 最终成绩优先采用已完成教师分，否则采用已完成且有效的学生互评分。
- 第一阶段继续使用现有 PDF、Markdown 和图片预览能力。
- 第一阶段不统一文件格式、不引入 PDF.js、不建设 Office 转码、不实现定位批注。
- 定位批注作为独立可选第二阶段，在确认业务价值后再实施。
